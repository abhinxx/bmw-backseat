# Backseat · Architecture

How the app is built, where the data comes from, and how the AI stays grounded.
Live: https://bmw-backseat.vercel.app · status as of 2026-10-11.

## 1. System

```mermaid

  PM(["PM in the browser"]) --> APP["Next.js 16 app<br/>Vercel, Frankfurt"]
  APP -->|"read-only, anon key"| DB[("Supabase Postgres<br/>Frankfurt")]
  APP -->|"/api/what-if, service key"| DB
  APP -->|"/api/what-if"| LLM["OpenAI gpt-6-luna<br/>reasoning effort: medium"]
  subgraph pipeline["Offline data pipeline, run by the team"]
    RAW["BMW files<br/>xlsx · pdf"] --> CLEAN["scripts/ingest-feedback.ts<br/>scripts/load-internal.ts"]
    WEB["Public web<br/>via Linkup search API"] --> EXT["verified JSON<br/>data/external/"] --> LOADX["scripts/load-external.ts"]
    REPORT["BMW Group Report 2025 PDF"] --> EXT
  end
  CLEAN --> DB
  LOADX --> DB
```

- Every push to `main` deploys to production. There is no separate staging.
- The browser only ever reads. Writes happen in two places: the loader scripts (run by the team) and `/api/what-if` (saves each run).
- The database does all counting. The AI never produces a number shown on a dashboard.

## 3. What-If: how a simulation runs (current)

```mermaid
sequenceDiagram
  participant PM
  participant API as /api/what-if
  participant DB as Supabase
  participant AI as gpt-6-luna
  PM->>API: "Make rear-seat heating standard"
  API->>DB: same question + model + versions run before?
  alt evidence unchanged
    DB-->>API: stored run
    API-->>PM: stored answer (no AI call)
  else new
    API->>AI: prompt 1: question to structured change (pick 1 of 16 features)
    AI-->>API: feature = rear_comfort, type = make_standard
    loop 9 personas in parallel
      API->>DB: evidence_comments() + study + price list (fixed query)
      DB-->>API: rows with IDs
      alt fewer than 3 comments and no study data
        API->>API: "Not enough evidence", no AI call
      else
        API->>AI: prompt 2: persona profile + evidence list
        AI-->>API: verdict + supporting / opposing IDs
        API->>API: drop IDs not in the list (logged as rejected), cap confidence
      end
    end
    API->>DB: save run + 9 verdicts + exact evidence
    API-->>PM: verdicts, each opens its evidence
  end
```

**Feature map** (`lib/features.ts`): 16 features, each linked to BMW feedback categories, a keyword pattern, survey questions and price-list option codes. It decides which evidence a persona sees.

**Persona scope** (`lib/simulate.ts`): which countries and engine types each persona stands for, taken from the persona files' market and cohort fields.

## 4. Grounding rules

1. The database selects the evidence, the same way every time for the same question.
2. The model sees only that evidence. Each item has an ID.
3. The model must cite IDs. The server drops any ID that was not given and stores it as rejected. No valid citation means no verdict.
4. Too little evidence means "Not enough evidence" without asking the model.
5. Same question + same evidence returns the stored answer. Repeatability comes from this cache, not from the model.
6. Every run is stored with the model, prompt version, feature-map version and an evidence fingerprint.

## 5. Current vs proposed (agentic search)

Today the model does not search. Code picks the evidence and the model reads it. The proposal gives the model read-only search tools over the same database.

```mermaid
flowchart LR
  subgraph Proposed
    A["persona agent"] -->|"search_comments"| D[("Supabase")]
    A -->|"get_survey"| D
    A -->|"get_options"| D
    A -->|"get_public: owner quotes, competitors, report"| D
    D -->|"rows + IDs"| A
    A -->|"verdict + IDs from its own tool results"| C["server citation check + tool-call log"]
  end
```

| | Current: fixed retrieval | Proposed: agentic search |
|---|---|---|
| Who picks the evidence | Code, via the feature map | The model, by calling search tools (max ~5 steps) |
| Same question, same evidence | Yes, always | No; the cache makes a repeated question identical |
| Finds evidence the map misses | No | Yes |
| Uses public data (owner quotes, competitors, report) | No | Yes |
| Speed and cost per question | ~20 s, up to 10 model calls | ~3-5x more calls |
| Audit trail | Evidence list per persona | Every tool call and its rows, per persona |
| Risk | Thin evidence when the map is incomplete | Less predictable; needs a step and cost cap |

## 6. Known limits

- Prompts in `lib/simulate.ts` are first drafts (`whatif-v2`); a reviewed rewrite is pending.
- The feature map and persona scope were drafted by Claude and are not yet reviewed by the team.
- `/api/what-if` has no rate limit yet (on the backlog).
- Personas exist for the 5 Series (G60) only.
- Public data is in the database but not yet shown on any screen.

## 7. Research Agent (planned, not built yet)

Today Linkup is not connected to the app. It was only used offline to collect the public data in section 2. The Research Agent is the live version: it searches the web with Linkup on demand and feeds what it finds back into the product.

```mermaid
flowchart TB
  PM["PM starts a run: vehicle, mission, question"] --> S["Server: Linkup search, standard or deep"]
  S --> X["Model extracts findings: claim, verbatim quote, URL, date, source type"]
  X --> V{"Quote found in the page Linkup returned?"}
  V -- "no" --> D["Dropped and logged"]
  V -- "yes" --> C["Classify: which of the 16 features, and agrees / contradicts / new signal vs BMW data"]
  C --> H["History: every run and every finding, always"]
  C -- "maps to a feature" --> M["Mission Control: Outside view feed and that feature's evidence, labelled External with source and date"]
```

Rules:

1. Every run and every finding is saved to History, whether or not it maps to a feature.
2. Web findings never change dashboard numbers. Counts come from BMW data only. Findings appear beside them, labelled External, with source and date.
3. Findings are mapped with the same 16-feature map as What-If, so a finding about rear-seat heating lands next to the rear-comfort evidence.
4. A quote that is not in the page Linkup returned is dropped.
5. Each run has a cap on Linkup calls.
